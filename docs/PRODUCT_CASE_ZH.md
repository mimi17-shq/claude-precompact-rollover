# 产品案例：在 Claude Code 自动压缩前安全接续长会话

## 一句话介绍

`claude-precompact-rollover` 面向 Claude Code 长会话：在上下文自动压缩前，保留最近若干完整的用户—助手原始轮次，生成经过内容校验的新会话；如果大段工具输出意外触发压缩，也可以从原始 transcript 中进行救援。

它不让另一个模型重新总结历史，也不会自行停止或重启 Claude。核心目标是让“保留了什么、是否完整、何时可以切换”都能被机械验证。

## 问题背景

长会话接近上下文上限时，Claude Code 可能自动压缩历史。摘要能够保留大意，但用户原始措辞、语气、最近任务中的细节和例外条件可能丢失。

工具调用还可能一次产生大量输出，使会话突然越过安全区间。手动复制最近对话也不够可靠：可能截断尚未完成的回复，混入工具输出、Thinking 或自动压缩摘要，甚至把旧窗口的 Usage 高水位带入新会话。

## 需求与成功标准

- 在默认 200k 上下文中，分别于 140k、155k 和 160k Token 进入准备、警告和换窗准备阶段。
- 只在助手完整回复结束、源文件至少稳定 15 秒后重建。
- 默认保留最近约 12,000 Token 的完整问答，不从一轮中间截断。
- 排除工具输出、Thinking、自动压缩摘要和旧 Usage。
- 新旧可见正文的 SHA-256 摘要必须完全一致。
- 解析、配对、SDK Fork 或摘要验证任一步失败时，不生成可切换目标。
- 核心程序不修改源 transcript，也不自行结束或重启 Claude。

## 方案设计

默认流程是：**监控用量 → 分阶段提醒 → 等待完整回复 → 备份源文件 → 筛选完整轮次 → Fork 新 Session → 校验正文摘要 → 输出下一窗口清单**。

达到 140k 时，工具提醒当前模型先整理需要长期保存的信息；155k 时再次警告；160k 后等待当前回复完整结束，再开始重建。如果已经检测到新的 `compact_boundary`，则优先进入压缩后救援，从原始追加式 transcript 中提取压缩前的真实问答。

重建时从最近一轮向前选择，直到达到配置的保留预算。为了保证语义完整，实际结果可能略微超过预算。生成目标 Session 后，工具会比较源内容和目标内容的摘要；只有完全一致时，才写出 `next-window.json`，交给用户或外部 Supervisor 决定何时切换进程。

配置为 1M 上下文的模型默认关闭自动换窗，只保留手动救援提示，避免把 200k 模型的阈值假设套用到更大的窗口。

## 关键决策与取舍

- 保留原文而不是生成摘要：可保留语气和细节，并能机械验真；代价是无法无限保留历史。
- 只保留完整问答：可能略超 Token 预算，但不会截断任务。
- 提前提醒写长期记忆：长期记忆负责跨窗口事实，最近原文负责短期对话连续性。
- 不在核心程序中自动重启 Claude：适配终端、tmux、systemd 或聊天桥接等不同运行方式，也减少误切窗口风险。
- 固定 Agent SDK 版本：提高当前版本的复现性，但需要持续跟进 Claude Code 和 SDK 的格式变化。

## 验证与局限

公开版本包含 9 项自动化测试，覆盖阈值状态机、未完成回复等待、压缩后救援、1M 模型策略、完整轮次选择、非法配置拒绝，以及使用合成 Session 经过 Agent SDK Fork 后的摘要一致性。冻结依赖环境下，9 项测试和 CLI、Rebuild 两个构建入口均已通过。

当前局限包括：保留 Token 使用估算算法而非官方 tokenizer；依赖 Claude Code 本地 transcript 和 Agent SDK 的当前结构；`next-window.json` 只负责交接，没有外部 Supervisor 时仍需用户手动启动目标会话；尚无外部用户规模、平均恢复时间或长期成功率数据。

## 我的职责

- 提出“压缩前主动换窗、压缩后仍能找回最近原文”的需求。
- 定义阈值状态机、完整轮次保留、文件稳定时间、摘要校验和 1M 模型策略。
- 明确安全边界：不修改源记录、不自动结束 Claude、校验不一致时不交付目标。
- 使用 AI 辅助完成 CLI、重建流程和自动化测试；我没有独立编写这些代码，也不将 AI 完成的编程描述为个人独立开发。
- 以完整轮次、摘要一致、Usage 清理和压缩摘要排除作为验收标准。
