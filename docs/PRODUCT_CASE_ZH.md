# 产品复盘：在 Claude Code 自动压缩前安全接续长会话

## 使用场景

我的主要使用环境是 Telegram 风格的移动端前端，后面连接一个 200k 上下文的 Claude Code 长会话。相比只在终端里使用，我更希望在手机上看到明确的记忆提醒、换窗预告、下一窗口模型与 effort 选择，以及换窗完成后的连续对话。

锚点、隐藏指定轮次和主动规划换窗属于我的前端集成体验；本公开仓库提取的是可复用的换窗核心，并不包含这套完整前端。

## 改造前的体验

最早的方案只是每天重启一次窗口。一天内同一窗口通常仍会自动压缩约两次。自动压缩由主模型执行，等待时无法继续自然交流，也很难确认摘要遗漏了哪些原话和细节。

根据我的长期使用观察，每次自动压缩通常需要约 1–2 分钟，并消耗至少约 2% 的周额度。改成按最近 X Token 主动换窗后，一次换窗通常约 20 秒；相比被动压缩，我体感一周额度消耗下降约 20%。这些是个人日常使用记录，不是严格对照实验，因此只作为问题价值和后续验证方向，不作为普遍结论。

## 我坚持的产品原则

### 1. 工具调用必须与对话正文分离

在 Channel 环境中，工具调用和工具输出往往比用户与助手的文字占用更多上下文。如果换窗时原样继承这些过程数据，新窗口很快又会被填满，用户真正需要继续的对话反而只占很小一部分。

因此我坚持保留完整的用户—助手文字轮次，同时剥离工具输出、Thinking、自动压缩摘要和旧 Usage。目标不是复制整个旧窗口，而是保留用户能够感知和继续使用的内容。

### 2. 超大工具调用冲破阈值后仍要能救援

仅设置“到 160k 就换窗”还不够。一次大型工具结果可能让上下文直接越过安全区间并触发压缩，监控来不及走正常流程。因此我把压缩后救援视为核心能力：检测到新的 `compact_boundary` 后，从原始追加式 transcript 中找回压缩前的真实问答，而不是继续依赖自动摘要。

### 3. 保留 X Token，而不是宣称 12k 是最优答案

不同对话的密度不同，固定保留轮数并不合理。我选择按最近 X Token 规划换窗，同时保证每个问答完整保留。公开配置中的 12k 只是 Codex 在实现阶段提出、由我接受的保守默认值，目前没有数据证明它是最优值，所以必须允许用户调整。

## 从需求到方案

Codex 根据上述需求提出了 140k 准备提醒、155k 紧急提醒、160k 换窗，等待源文件稳定 15 秒，以及用 SHA-256 比较新旧可见正文等实现方案。我认可这些设计，因为它们分别解决了长期记忆准备、避免截断当前回复、避免读取半成品和机械验真问题。

完整流程是：

1. 日常对话继续进行，140k 时提醒当前模型先整理长期记忆。
2. 155k 时提示即将换窗，并允许前端询问下一窗口的模型和 effort。
3. 等待当前助手完整回复、源文件稳定后，备份原 transcript。
4. 剥离工具过程，按 X Token 选择最近的完整问答。
5. 通过 Agent SDK Fork 新 Session，并比较源目标正文摘要。
6. 校验通过后输出 `next-window.json`，由前端或 Supervisor 完成切换。
7. 新窗口继续原话题；核心程序本身不擅自停止或重启 Claude。

如果超大工具调用提前触发压缩，流程跳到救援模式，从原 transcript 重建最近原文。

## 使用后的变化

用户体验从“突然等待压缩，之后只能相信一段摘要”变成了一个可预期过程：先收到写记忆提醒，再看到换窗预告和模型选择，随后收到完成提示，并继续上一段对话。

公开版本的 9 项自动化测试证明阈值状态机、完整轮次选择、压缩后救援和摘要校验可以运行；它们不等同于体验改善。体验改善的依据目前主要来自我自己的长期使用观察，下一步应记录每次压缩与换窗的耗时、额度变化、保留轮次和是否需要人工补充上下文，再做更可靠的对比。

## 局限与后续计划

- Token 保留量使用估算算法，不是官方 tokenizer 的精确结果。
- 依赖 Claude Code transcript 和 Agent SDK 的当前结构。
- Telegram 风格前端、锚点、隐藏和规划界面不包含在本公开仓库中。
- 20% 周额度改善是个人体感，仍需连续记录进行验证。
- 没有外部用户样本，尚不能证明这套阈值适合其他人的使用节奏。

## 我的职责

- 提出压缩前主动换窗和压缩后原文救援需求。
- 坚持剥离工具调用、保留完整文字轮次和 X Token 可配置。
- 定义移动端应呈现的记忆提醒、换窗预告、模型/effort 选择和完成反馈。
- 评估并接受 Codex 提出的默认阈值、稳定窗口、摘要校验和外部接管方案。
- 根据个人长期使用对等待时间、额度消耗和对话连续性进行验收。
- 代码实现和自动化测试由 AI 完成；我没有独立编写这些代码。
